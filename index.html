IDENTIDADE DO SISTEMA O sistema será denominado: # LotoCE Quant Lab V4.0 — LQIP LQIP significa: **LotoCE Quant Intelligence Platform** O sistema é um laboratório quantitativo destinado a: * ingestão de dados; * limpeza; * normalização; * análise estatística; * análise temporal; * descoberta de padrões; * modelagem probabilística; * machine learning; * simulação; * backtesting; * comparação com baseline; * consenso entre modelos; * ranking de milhares; * avaliação contínua dos modelos; * auditoria e explicabilidade. --- # 2. OBJETIVO CIENTÍFICO O objetivo NÃO é afirmar que um resultado futuro pode ser conhecido com certeza. O objetivo é: > encontrar, medir, testar e validar evidências estatísticas que possam produzir uma classificação relativa das milhares, verificando se essa classificação apresenta desempenho diferente do esperado pelo acaso quando submetida a backtesting rigoroso. O sistema deve trabalhar com: * probabilidade; * evidência; * incerteza; * validação; * comparação; * desempenho fora da amostra. Nunca apresentar uma previsão como certeza. Nunca afirmar: > "Esta milhar vai sair." Utilizar linguagem como: > "Esta milhar apresentou maior score relativo segundo os modelos atualmente validados." --- # 3. PROBABILIDADE TEÓRICA Para milhares de quatro dígitos: ```text 0000 0001 0002 ... 9999 ``` existem 10.000 possibilidades. A probabilidade teórica uniforme de uma milhar específica em uma posição específica é: ```text 1 / 10.000 ``` ou: ```text 0,01% ``` Essa referência deve existir no sistema como **baseline teórico**. Não confundir: ```text probabilidade matemática teórica ``` com: ```text score estatístico ``` ou: ```text probabilidade estimada/calibrada por modelo. ``` --- # 4. REGRA FUNDAMENTAL — BASELINE Todo modelo deve ser comparado contra pelo menos: ### Baseline A — Uniforme Todas as milhares possuem a mesma probabilidade teórica. ### Baseline B — Frequência histórica Ranking baseado apenas em frequência histórica. ### Baseline C — Frequência recente Ranking baseado apenas em janela recente. Quando aplicável, criar outros baselines. Um modelo só pode ser considerado potencialmente útil se demonstrar desempenho superior aos baselines de forma consistente e fora da amostra. --- # 5. REGRA FUNDAMENTAL — RECÊNCIA O sistema deve dar **forte importância ao comportamento recente**, porque o objetivo é avaliar o estado atual do processo. Porém, não deve simplesmente ignorar o histórico antigo. Utilizar simultaneamente: ## LONGO PRAZO Todo o histórico disponível. ## MÉDIO PRAZO Janela configurável. ## CURTO PRAZO Janela configurável, com maior peso para dados recentes. Implementar: * rolling windows; * frequência recente; * frequência histórica; * frequência ponderada; * EWMA; * exponential decay; * recency score; * comparação recente vs histórico; * mudança de regime; * change points. --- # 6. PRINCÍPIO DA RECÊNCIA ADAPTATIVA Não assumir antecipadamente que: > "os últimos X resultados são sempre melhores." O sistema deve testar qual janela apresenta melhor desempenho no backtesting. Exemplo: ```text 50 concursos 100 concursos 250 concursos 500 concursos 1000 concursos histórico completo ``` Essas janelas devem ser configuráveis. O backtesting deve determinar quais janelas apresentam melhor estabilidade. --- # 7. NÃO criar: ```text database_manha database_tarde database_noite ``` NÃO criar históricos separados. A sessão é apenas uma dimensão do evento. Exemplo: ```text 13/07/2026 MANHA 13/07/2026 TARDE 13/07/2026 NOITE ``` São três eventos diferentes dentro da mesma linha temporal. --- # 8.
